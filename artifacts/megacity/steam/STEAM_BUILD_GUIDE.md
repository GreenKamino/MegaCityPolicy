# MEGACITY — Steam Build & Upload Guide (Windows)

This folder contains everything needed to package **MEGACITY: Sector Marshal** as a
Windows desktop app (Electron) and upload it to Steam.

- **App ID:** `4633600`
- **Windows content depot:** `4633601`
- **Target:** Windows x64 only

> The actual Windows packaging (`build:win`) and the SteamPipe upload **must be run on
> a Windows machine** with the Steam SDK. They cannot be done from the Replit Linux
> sandbox (electron-builder needs Wine for the Windows installer, and the upload needs
> your Steam login + 2FA). Everything that *can* be prepared here already has been —
> see "What's already done" below.

## Refresh the web bundle and downloadable files

After changing the game, run these two commands from the full Expo project root
(`artifacts/megacity`):

```bash
pnpm run steam:refresh-web
python3 steam/scripts/repack-deliverables.py
```

The first command exports into `steam/web-build-new`, inlines fonts, applies the
Windows MAX_PATH asset flattening, verifies the entry bundle, checks that no
`__node_modules` paths remain, confirms the longest Windows path is under 260
characters, and safely swaps the prepared bundle into `steam/web-build`. The
second command rebuilds and verifies all three downloadable ZIPs. Neither
command rebuilds the Electron Windows runtime; that remains a Windows-only step
when native or Electron configuration changes.

### Important fix applied
The Expo web export emits **root-absolute** asset paths (`/_expo/...`, `/favicon.ico`).
Loading `index.html` directly via `file://` would make every asset 404 (this would have
shown a black/blank window on Windows too — not just Linux). `main.js` now serves the
bundle through a privileged in-app `app://` protocol, which preserves absolute-path
semantics relative to `web-build/`. This is the standard Electron pattern and fixes both
the initial load and the lazy-loaded chunks (achievement report, keyboard help, etc.).

## Prerequisites (your Windows machine)

1. **Node.js 18+** and **npm**.
2. **Git Bash** (optional, lets you run `build-steam.sh` directly) — or just use the
   manual steps below in PowerShell/CMD.
3. **SteamCMD** — download from
   https://developer.valvesoftware.com/wiki/SteamCMD and unzip somewhere on PATH.
4. Be a member of the MEGACITY app on Steamworks with **Edit App Metadata** +
   **Publish** permissions.

## Step 1 — Build the Windows app

> **This kit already includes a pre-built web bundle** (`web-build/`), exported from the
> current game. If you're building from this standalone kit, **skip the Expo export** and
> go straight to `npm install` / `npm run build:win`. You only need to re-export if you
> have the full Expo project and have changed the game.

### Option A: one command (Git Bash)
```bash
cd steam            # the folder you extracted from the kit
./build-steam.sh    # detects the pre-built web-build, skips the export, runs build:win
```

### Option B: manual (recommended for the standalone kit)
```bash
# from the extracted steam/ folder — web-build/ is already present
npm install             # installs electron 39 + steamworks.js + electron-builder
npm run build:win       # produces dist/win-unpacked/  and an NSIS installer
```

### (Only if you have the full Expo project and changed the game) re-export first
```bash
# from artifacts/megacity (the Expo project root)
pnpm run steam:refresh-web
# then rebuild the Windows app only when native/Electron files changed:
# cd steam && npm install && npm run build:win
```

### Refreshing the downloadable deliverables (full Expo project only)
After the export above, one script rebuilds all three zips in `dist-download/`
(the Windows build, the uploader, and this build kit), stamps the current app
version into the Windows build, records the exact web entry bundle in
`release-manifest.json`, and verifies the result:
```bash
# from artifacts/megacity (the Expo project root)
python3 steam/scripts/repack-deliverables.py
```

The manifest is human-readable, versioned JSON with the app version, build ID,
entry bundle filename, and a sorted SHA-256/byte-size inventory of the immutable
web-build assets and Electron shell resources. The manifest itself (and any
future signature) is deliberately excluded to avoid self-reference; user saves
and other mutable data are not included. It is copied into the Windows app
payload, the build kit, and the uploader ZIP. On packaged startup Electron
checks every inventory entry before loading the BrowserWindow. Missing or
changed files produce a visible warning, keep offline play available, and
disable achievement/stat writes until the installation is repaired.

This is tamper evidence for casual packaged-file edits, incomplete installs, and
stale release payloads — **not unbreakable DRM**. A determined person who can
modify the installation can also replace the local manifest, so this check does
not provide cryptographic authenticity or prevent reverse engineering. It does
not phone home, require an online connection, or contain private keys/secrets.

Result: **`steam/dist/win-unpacked/`** — this unpacked folder is what gets uploaded to
Steam. The launchable executable inside it is **`game.exe`** (set via `executableName`
in `package.json`). This name must match the **Launch Option** you configure on
Steamworks (Installation → Launch Options → Executable = `game.exe`), and it is exactly
what Steam's **"Public Default Branch Includes 'game.exe'"** checklist item scans for.
(The NSIS `.exe` installer that's also produced is **not** needed for Steam; it's only
useful for distributing outside Steam.)

> Tip: if you only want the unpacked folder and want to skip making the installer, run
> `npx electron-builder --win dir` instead of `npm run build:win`.

## Step 2 — Test locally before uploading

```bash
cd artifacts/megacity/steam
npm start
```
The game window should open and load to the main menu. With the Steam client running and
`steam_appid.txt` (= `4633600`) present, the console logs
`[Steam] steamworks.js initialized for App ID 4633600`. Without Steam it logs
`running in offline mode` and still plays — saves fall back to local storage.

Sanity checklist:
- [ ] Main menu renders (not a black window).
- [ ] Start a game; open the keyboard-help and an achievement/tick report modal (these are
      the lazy-loaded chunks — they confirm the `app://` protocol serves runtime assets).
- [ ] Resize/maximize, quit, relaunch → window position is remembered.

## Step 2b — Windows release-runner Steam Cloud restore check

The packaged Cloud restore smoke test runs on a dedicated **Windows x64 runner**
with the Steam client already running and logged into a test account. It uses
the actual `steamworks.js` native module from the release build, rather than the
Linux-safe disposable fixture used for local development.

The runner must:

1. Have Node.js 20+, Windows x64, and the Steam client installed.
2. Keep Steam running and logged in to an account that can launch App ID
   `4633600`, with Steam Cloud enabled for the app.
3. Use a dedicated Steam account/app Cloud area. The check refuses to run when
   another Cloud file is present, so it cannot delete a player's saves.
4. Register the labels `self-hosted`, `windows`, `x64`, and `steam` used by
   `.github/workflows/steam-cloud-restore.yml`.

The Steam Cloud workflow installs the standalone dependencies in this folder,
builds `dist/win-unpacked/game.exe`, and runs the check on release publication,
manual dispatch, and a weekly scheduled run (Mondays at 03:00 UTC). A hosted
freshness check runs one hour later (04:00 UTC) and allows an eight-day
freshness window. This catches a restore workflow that is still queued because
the Windows runner is offline, without waiting on that runner itself.

The freshness check reports distinct states:

- `RUNNER_OFFLINE` — the latest restore job is queued and no
  successful restore completed within the eight-day window.
- `RUNNER_PENDING` — the latest restore is still in progress; it is reported
  separately from a failed test and becomes an error if the freshness window
  has expired.
- `TEST_FAILURE` — the latest restore job completed unsuccessfully.
- `FRESHNESS_MISSED` — no successful scheduled restore completed within the
  window and the latest restore is not simply queued.

The check also emits `RUNNER_PENDING` as a warning when a current restore is
queued but the previous successful restore is still inside the window.
Scheduled restore runs use a separate `Scheduled Steam Cloud restore (Windows
x64)` CI check, while release and manual runs retain the existing check name.

The freshness decision logic is also covered by a standalone, Steam-client-free
fixture harness. It runs automatically in the `Steam Cloud freshness logic`
GitHub Actions check when the workflow or checker changes, and can be run
locally from the repository root:

```bash
bash artifacts/megacity/steam/scripts/test-cloud-freshness.sh
```

The fixtures cover a queued restore, an in-progress restore, a completed failed
restore, a recent successful restore, and an expired successful restore. They
assert the expected `RUNNER_OFFLINE`, `RUNNER_PENDING`, `TEST_FAILURE`,
`FRESHNESS_MISSED`, and passing states without contacting GitHub or Steam.

The restore command is:

```powershell
$env:MEGACITY_RUN_PACKAGED_CLOUD_RESTORE = "1"
.\artifacts\megacity\steam\run-packaged-cloud-restore.ps1
```

The resulting log records real Steamworks initialization, Cloud enabled status,
the exact disposable envelope bytes in base64, the one-file count before
cleanup, the absence of normal local save/profile keys, and cleanup of both
temporary directories. The disposable Cloud file is also removed through the
bridge before the packaged process exits.

## Step 2c — Windows release profile-slot cleanup check

The unpacked Windows release build also has a dedicated profile-save cleanup
smoke test. It uses the actual `dist\win-unpacked\game.exe` twice: the first
launch seeds a complete commander profile, primary slot, backup slot, and a
stale `.tmp` key; the second launch uses the normal startup path and verifies
that the `.tmp` key is removed while both save envelopes remain valid and
loadable.

The check is isolated from a runner user's normal Steam data:

- It requires a Windows x64 runner and the unpacked `game.exe`.
- Puppeteer passes a fresh temporary `--user-data-dir` to both launches, so
  AppData storage for the fixture never uses the normal MEGACITY profile.
- The fixture is seeded through the renderer's real `app://` localStorage and
  is deleted with the temporary profile after the check.
- Release mode verifies the packaged `release-manifest.json` and entry-bundle
  SHA-256 before testing storage behavior, catching a stale shipped bundle.

After building the unpacked release (`npm run build:win -- --publish never`),
run from PowerShell:

```powershell
.\artifacts\megacity\steam\run-packaged-profile-tmp-cleanup.ps1
```

The script records output in
`artifacts\megacity\steam\packaged-profile-tmp-cleanup.log`. The
`Windows Profile Slot Cleanup` workflow runs the same check on release
publication, manual dispatch, and a weekly scheduled run.

The LA CITY migration check also writes
`packaged-la-city-legacy-save-summary.json`. The JSON records the decoded LA
CITY values after resave and process restart, the retired `KHANATE` and
`TORGRIM` presentation checks, the v2 envelope checks, renderer errors, and
whether the disposable profile directory was removed. The Windows workflow
uploads that summary together with the full
`packaged-la-city-legacy-save.log` and the packaged
`dist\win-unpacked\release-manifest.json` as the
`packaged-la-city-migration-evidence` artifact, with a 90-day retention period.
The release manifest names this artifact so the evidence can be matched to the
exact Windows build that produced it.

## Step 2d — Windows release train-module save/reload check

The unpacked Windows release build also checks the rail upgrade persistence path.
It starts a deterministic completed Irongate corridor, installs armored train
plating, troop-transport carriages, and weaponized escort cars through the real
diplomacy controls, then saves and reloads the same isolated slot. The check
asserts both the wrapped save envelope and the Overview diagnostics:

- all three installed module IDs survive reload;
- safety resilience remains `+25`;
- armed-security benefit remains `+16`;
- troop-transport capacity remains `40`; and
- no normal profile or player slot keys are created or changed.

The runner passes a fresh temporary Electron `--user-data-dir` to both
launches and deletes it in a `finally` block, so normal player saves are not
touched. After building the unpacked release, run:

```powershell
.\artifacts\megacity\steam\run-packaged-rail-modules.ps1
```

## Step 2e — Windows release legacy production check

The same Windows x64 release workflow automatically runs the packaged legacy
production smoke test immediately after building the unpacked game. It opens
the real production-chain screen with a legacy save fixture that has no
civilian production buildings or military installations, then verifies:

- civilian supply and demand remain at zero and every production card remains
  `NOT BUILT`;
- military production remains at zero and does not render a civilian balance;
- the packaged release manifest and entry-bundle hash match the source; and
- the fixture leaves the runner user's real profile and save slots untouched.

The production fixture receives its own temporary Chromium user-data directory
and removes it after the test, so it cannot read or modify normal player data.
The workflow fails when either civilian or military production facts drift, and
uploads `packaged-production-chains-legacy.log` as the
`packaged-production-chains-legacy-log` release artifact even when the check
fails. The profile-slot cleanup log is uploaded separately.

To run the same packaged check manually after building
`dist\win-unpacked\game.exe`:

```powershell
.\artifacts\megacity\steam\run-packaged-production-chains-legacy.ps1
```

The `Windows Profile Slot Cleanup` workflow runs all packaged checks on
release publication, manual dispatch, and its weekly scheduled run.

The same workflow also has a hosted weekly freshness check at 04:30 UTC. It
queries the GitHub Actions API for a successful `Packaged profile-slot cleanup
(Windows x64)` job from the 03:30 UTC schedule and fails with
`FRESHNESS_MISSED` when the last success is older than eight days. The
freshness job runs on `ubuntu-latest` without depending on or waiting for the
dedicated Windows runner, so an offline runner or missing canonical workflow
produces an alert before the next release.

## Step 2e — Windows release contract recovery check

The same dedicated Windows x64 release runner also launches the unpacked
`dist\win-unpacked\game.exe` against the active-contract fixture. It verifies
that the real `app://` packaged renderer shows the stalled housing award's
projected `+525 cr` scrap recovery and explicitly says that voluntary
cancellation remains non-refundable.

The check is isolated from real player data:

- Puppeteer gives the release process a fresh temporary `--user-data-dir`;
- the fixture is read-only and the test asserts that no player profile or slot
  keys were created; and
- the temporary profile is deleted after the run, including on assertion
  failures.

The release check also compares the unpacked release manifest and entry-bundle
SHA-256 against the source manifest before opening the app, so a stale
`web-build` cannot produce a false pass.

After building the unpacked release (`npm run build:win -- --publish never`),
run from PowerShell:

```powershell
.\artifacts\megacity\steam\run-packaged-contract-recovery.ps1
```

The `Windows Profile Slot Cleanup` workflow runs this check after the existing
packaged checks on release publication, manual dispatch, and its weekly
scheduled run. Its output is recorded in
`artifacts\megacity\steam\packaged-contract-recovery.log`.

## Step 4 — Upload the build via SteamPipe

```bash
cd artifacts/megacity/steam
steamcmd +login <your_steam_username> +run_app_build "%CD%\app_build_win.vdf" +quit
```
(On Git Bash: `steamcmd +login <user> +run_app_build "$(pwd)/app_build_win.vdf" +quit`.)

- Use **`app_build_win.vdf`** (Windows-only). The older `app_build.vdf` also references
  mac/linux depots and will fail unless you've built those too.
- `ContentRoot` is `"."`, so **run steamcmd from this `steam/` folder** (or edit the vdf
  to an absolute path) so `dist/win-unpacked/*` resolves.
- First run will prompt for your Steam Guard 2FA code.

After it finishes:
1. Steamworks → your app → **Builds** → set the new build live on the **`default`**
   branch (the public default branch). The **"Public Default Branch Includes 'game.exe'"**
   checklist item only turns green once a build that contains `game.exe` is **live on
   `default`** — uploading alone is not enough, and setting it live only on a `beta`
   branch will not satisfy the check.
2. **Publish** the change.

> **Already uploaded a build whose executable is named `MEGACITY.exe`?** Two ways to fix it:
> - **Fastest (no rebuild):** in your existing `dist/win-unpacked/` folder, rename
>   `MEGACITY.exe` → `game.exe` (leave every other file as-is — Electron locates its
>   `resources/` by folder, not by the exe's name), re-run the SteamPipe upload above,
>   then set that build live on `default`.
> - **Clean (rebuild):** re-run `npm run build:win` with the updated config — it now
>   outputs `game.exe` directly — then upload and set the build live on `default`.
>
> Either way, confirm the Steamworks **Launch Option** executable is set to `game.exe`.

## Notes

- **Code signing is optional for Steam.** Steam delivers and launches the game through its
  own client, so an unsigned Electron build is fine. (Signing only matters if you also hand
  out the raw `.exe` outside Steam, where Windows SmartScreen may warn.)
- **`steamworks.js` is optional at runtime.** If it fails to load, the game runs in offline
  mode — achievements/cloud just no-op. Real achievements require the Steam client running
  and the SDK present (it is, in `sdk/`).
- This `steam/` folder uses its **own npm lockfile** (`package-lock.json`), independent of
  the pnpm workspace, to manage the Electron/electron-builder/tar version bumps.
